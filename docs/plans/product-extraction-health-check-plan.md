# Product-data extraction health check and treatment — Implementation Plan

## Summary

**Decision: measure with the mechanisms already present; do not replace extraction or enable new traffic.** The repository has mature, fail-closed profile version-health and activation/release checks, plus a retained-artifact, no-refetch profile audit harness. Packaging OCR/VLM has a useful versioned candidate-versus-baseline evaluation gate, but the committed Bay State gold set contains **8 entries**, below its **≥30-image model-change floor**. Distributor-record materialization is a separate, provenance-bound, **no-fetch** route, not a fallback web scraper. **Current live quality, model quality, production latency, failure rates, and cost were not measured.** There is no measured overall health score.

Evidence for these starting findings: `src/onboarding/domain-version-health.ts:1-45,81-176,216-244`; `src/onboarding/profile-activation-gate.ts:44-195`; `src/onboarding/profile-audit/replay-runner.ts:1-18,70-129`; `src/onboarding/ocr-eval/datasets/packaging-ocr-baystate-golden.json:4-230`; `docs/runbooks/packaging-ocr-model-rollout.md:12-52`; `src/onboarding/sourcing/distributor-record-materializer.ts:154-175`.

**Current assessment:** repository safety/evaluation mechanisms are established; release-quality evidence sufficiency and current operational health must be assessed per path and scope. Priorities are (1) inventory and execute existing offline checks safely, (2) repair evidence gaps, (3) assess the user-facing readiness discrepancy and treat only confirmed problems, and (4) conduct separately authorized current-data qualifications. A green probe, a passing unit suite, an active profile row, or an eight-image OCR smoke result cannot substitute for qualification.

**Delivery boundary:** this document is the only artifact created by this assignment. No implementation, live crawl, provider/model call, model download, production mutation, build, lint, tests, or formatting was performed. Test and smoke evidence below are future requirements, not claimed results. Source inspection and the supplied operator observation are the basis of this assessment.

### Decision tree and execution prerequisites

1. **Can the intended operation run without network or protected-state writes?** Default: use explicit in-memory profile/manifest inputs and retained artifacts. If not demonstrably safe, stop that operation; do not start the API/worker to work around it.
2. **Are inputs independently labeled, versioned, representative, and sufficiently powered?** Default: exploratory report only until the evaluation owner freezes sample sizing and reviewer sign-off. Do not count circular labels as qualification.
3. **Is current-data validation requested and authorized for a specific path?** Default: no. The operator must supply scope, assets, privacy/source policy, budgets and a stop/rollback owner before that phase.
4. **Does evidence demonstrate a defect or just a missing measurement?** Default: investigate first; scope a minimal treatment only for the established defect. Missing data is not proof of a broken extractor.

## Spec

### S1. Goals, non-goals, and user stories

Goals: produce reproducible, strategy-specific baselines; distinguish extraction correctness from safe refusal and coverage; expose unavailable evidence; prioritize treatments by identity/source risk and user impact; qualify any later change through existing gates.

User stories:
- As an operator, I can see which scopes have reviewed evidence, which are blocked, and which were not measured without mistaking connectivity for quality.
- As an extraction engineer, I can replay identical retained bytes through existing configurations and diagnose field, image, identity and variant regressions without touching the catalog.
- As an OCR owner, I can qualify a candidate against the same frozen, adequately sized image set and baseline without changing the model during measurement.
- As a sourcing owner, I can distinguish connector retrieval qualification from deterministic record materialization and verify provenance without fetching anything.
- As a reviewer, I can reject unsupported conclusions because every result carries input/version provenance, denominators, uncertainty, and a clear execution mode.

Non-goals are those in Clarified Requirements. In particular, this health check does not authorize catalog promotion, connector enablement, live scraping, or an OCR model change.

**Important interpretation safeguards**

- **Complementary evidence layers, not interchangeable quality estimates:** the activation matrix compares output against manager-approved per-sample observations, with artifact binding (`src/onboarding/profile-test-matrix.ts:80-155`). That is valuable regression/qualification evidence, but it does not independently establish product truth or representative live accuracy. The separate `profile-audit` independent-label/holdout evaluation supplies that measurement layer. Reviewed health consumes stored matrix/observation evidence without recapturing pages (`src/onboarding/domain-version-health.ts:34-45,98-122,149-176`); “fresh” there means evidence binding, not proof that an upstream template is unchanged today. Any future recurring recapture needs separately measured need, source policy and operator authorization.
- Ladder `identityStatus` / `identityReasons` are diagnostics-only (ADR 0031:26), **not evidence that the entire pipeline has no identity gates**. Queue extraction rechecks the confirmed URL and `validateExtraction` before insertion (`src/onboarding/job-queue.ts:1974-2027,2065-2073`); variant errors have separate handling (`:2115-2163`). Benchmark the exact consumer path as well as the parser seam.
- A cached domain probe (`ok|blocked|offline|mismatch`) is not a quality score. Its getter can **delete** expired rows after seven days (`src/db/repositories/domain-status-repo.ts:24-58`); do not use it on protected inputs during a read-only audit.
- `structured_only` is the existing arm name, not a guarantee that only structured markup is parsed: it calls `extractProductFromHtml` with no CSS profile (`profile-audit/replay-runner.ts:203-223`), and that parser still includes HTML heuristics and images (`src/onboarding/page-extractor.ts:152-207`). Label reports accurately; do not infer a pure JSON-LD ablation.
- Third-party page prices are excluded from extraction and variant matching under ADR 0043; the onboarding value is the only price authority.

### S3. Read-only, network-off baseline procedure

This is the first future execution phase. No steps below have been executed as part of this document.

#### 1. Freeze scope, permissions and evidence inventory

Owner: extraction lead plus data reviewer; security/operator approves containment.

- Record code revision, profile/version/executable-policy hashes, schema/prompt/model identifiers and resolved model digests where available, flags/retry policy, hardware/runtime, artifact/label revisions and hashes, and the authorization record. Mutable model tags alone are not a reproducibility identifier.
- Obtain an operator-approved, consistent backup/export of the intended workspace with retained HTML/DOM/screenshots/payloads and accepted distributor evidence. Do not copy a live SQLite main file without its approved consistent-backup procedure. Redact secrets and restrict authenticated snapshots.
- Mount inputs read-only; deny network at process/sandbox level, including loopback; do not start API, worker, browser, Ollama or providers. Permit only explicit local report/temp outputs outside protected catalog paths. Snapshot source hashes before and after and retain a denied-network/write-attempt log.
- Inventory every intended sample, including unavailable, unreadable, stale or mismatched artifacts. Track `selected → artifact available → label reviewed → attempted → schema-valid → correct → served` denominators separately. No silent dropping or treating missing bytes as parser failure.
- Reuse existing repositories/export shapes for data access. `domain-version-health` is read-only by contract, but an audit must also establish a safe read-only **connection**. `initDb` opens the configured DB and sets WAL (`src/db/connection.ts:14-23`); it is not a proven read-only binding. If authoritative health cannot be evaluated safely, record **not evaluated** and resolve that invocation prerequisite, rather than duplicate health logic or initialize production state.

**Existing command caveat:** `scripts/run-pilot-audit.ts:23-48` and `scripts/build-audit-manifest.ts:27-54` target a workspace DB and write local reports; neither is an established read-only command for the current checkout. Do **not** run these unchanged against the operator workspace. Their presence is useful plumbing, not an authorization shortcut. Use the existing library interfaces with explicit supplied inputs. A missing safe operator invocation is a narrow engineering task, not a reason to build another benchmark.

#### 2. Establish independently reviewed, representative corpora

- Human/subject-matter reviewers label retained evidence **without seeing the extractor's answer first**. Record reviewer, adjudication, label version, source/capture time, immutable bytes/hash and expected item identity/variant. Auto-derived/unspecified labels remain exploratory and cannot qualify a change (`src/onboarding/profile-audit/promotion-eligibility.ts:142-207`). A source string or valid schema is not proof that a label was independently reviewed.
- Freeze a stable holdout split before tuning; keep whole product families/template relatives together to prevent sibling leakage. Report tuning, holdout and newly adjudicated failure cases separately. Retire contaminated holdouts only with a newly frozen revision and explicit review.
- Official-page strata: domain and template cluster, static versus rendered capture, product family, platform signals, single versus multi-variant/family-only page, wrong-product/variant and stale receipts, sparse/contradictory identifiers, image noise, blocked/offline artifacts, onboarding-price preservation and rejection of page-price data. Distinguish confirmed/candidate/profile-blocked inventory; do not let only successful PDPs define coverage.
- OCR strata: product department/family, bag/can/pouch/box and other actual package modalities, readable/occluded/small or blurred text, front/back imagery, missing/inapplicable fields, absent barcode versus readable UPC, conflicting brand/UPC across images, and supported operational no-image inputs. Labels must reflect **visible evidence**, not inferred catalog knowledge. Preserve omitted-versus-explicit-null semantics.
- Distributor strata: provider/connector and generation/catalog version, exact match and negative/wrong variant, variant-axis declarations, source error/auth failure, conflicting records, superseded generation, incomplete provenance and idempotent reuse. Review merchandising correctness separately from identity qualification. Include manual-evidence attestations in a separate integrity inventory.
- **Sample sizing:** evaluation owner pre-registers desired confidence/precision per decision-critical scope, expected prevalence, independent-family count, and treatment/non-inferiority rules **before** seeing comparison results. Use a scoped sampling calculation and increase samples when intervals remain inconclusive. The profile audit's generic minimum of 3 (`shared-metrics.ts:186-193`) and pilot default of 2 candidates (`pilot-auditor.ts:26-34`) are not a statistical health target. The CLI's sample limit of 5 is also not qualification. Do not import OCR's ≥30 floor into other paths or treat ≥30 as sufficient precision for every OCR stratum.

#### 3. Run existing official-page replay, not live extraction

- Supply an explicit frozen `AuditManifestSample` manifest and exact profile snapshot to `runPilotAudit({ domain, manifest, profile, artifactRoot, recordLatency: true })` (`src/onboarding/profile-audit/pilot-auditor.ts:26-69`). Do not permit its DB profile fallback (`:36-44`) or automatic manifest inventory to select unreviewed data silently. Where needed, use `replaySample` + `scoreExtraction` directly with the same existing report/gate modules; no new extraction/scoring engine.
- Replay all four existing configurations against identical bytes; retain row-level outputs, per-scope operator review, promotion-eligibility and strategy reports (`pilot-auditor.ts:71-125`). These reports are recommendations/evidence only: **no activation or promotion follows**.
- Preserve evidence gaps as gaps (`replay-runner.ts:75-105`). The harness's rejecting fetch seam (`:109-129`) complements external network denial; neither authorizes image URL resolution or a missing-HTML capture route. Use retained HTML, never a tooling route that may capture a live page.
- Repeat deterministic replays on the same inputs; compare scored identities excluding wall-clock latency (`replay-runner.ts:13-17`). Record repeat variability separately from changed datasets.
- Call this a **retained-artifact parser baseline**, not a full production-browser result. Rendered DOM artifacts do not exercise interactions, worker navigation, receipts, queue validation or persisted evidence. Existing isolated consumer tests provide that separate safety check; later authorized worker validation supplies current behavior.

#### 4. Use OCR evaluation only where feasible in true network-off mode

- First load/validate the existing gold JSON and digest, inspect image references, and inventory local image bytes with hashes/rights. The documented Bay State directory is unavailable at the path reported above; do not infer that assets do not exist elsewhere or attempt a download.
- The real runner stages images to a temp directory and invokes OCR **sequentially**, with required injected transport and loopback-only candidate URLs (`src/onboarding/ocr-eval/runner.ts:52-71,156-218,255-260`). Image resolution fails the run before any model call (`:171-180`). Preflight missing assets into a separate availability report; never silently shorten the dataset or count an unavailable input as an OCR parser defect.
- A mocked/pinned-response transport can exercise parser, metrics and gating machinery offline using existing fixture patterns. Such output is **harness correctness evidence, not current model performance**, and its latency cannot qualify a model. If no saved response/image exists, leave that execution unavailable; do not fabricate a baseline.
- Actual baseline/candidate inference requires explicit later loopback authorization, installed pinned models, complete image bytes and the frozen ≥30-image set. Eight examples may support a smoke/exploratory report only, **never the model-change gate**. Do not run the CLI as part of the strict network-off baseline.
- Reuse the OCR runbook for execution details, mitigations, stdout evidence and flip mechanics rather than copying its whole procedure into this plan.

#### 5. Audit distributor/manual evidence without materializing production rows

Use read-only accepted-evidence/provenance exports and existing projection/reconstruction seams to compare expected records and persisted payloads. Do not invoke transactional materializers, submission/withdrawal, release/retry, cohort freeze or promotion endpoints. Pure reconstruction is distinct from executing the persistence path (`src/onboarding/sourcing/distributor-record-materializer.ts:434-467`). Record missing generation/attempt/hash/attestation evidence as integrity gaps, not scrape failures. Test writers/transactional failures later only in isolated test databases. Connector retrieval quality requires connector-specific evidence; no-fetch materialization proves nothing about login or current supplier coverage.

**Existing OCR model-change gate — preserve unchanged:** same frozen ≥30-image dataset and comparable baseline; digit-exact UPC ≥ baseline −0.02; hallucination ≤ baseline; empty ≤ baseline +0.01; parse success ≥0.95; p95 ≤2× baseline. Run `evaluateRolloutGate` without weakening/retuning after results. The code fails missing comparison/sample requirements (`src/onboarding/ocr-eval/metrics.ts:308-374`); the registration is `docs/runbooks/packaging-ocr-model-rollout.md:12-52`. Retain all gate failures and uncertainty. Passing this gate is necessary for a model change, not authorization to flip automatically.

**Decisions:** `exploratory / needs evidence`, `no-go`, or `eligible for explicitly reviewed next phase`, scoped to the tested route/version/dataset. Existing profile activation and audit-promotion requirements remain authoritative; the health report cannot override them. Existing connector thresholds remain connector-only. No new global percentage or green score is imposed.

**Immediate no-go / stop conditions:**

- Any unexpected network call, protected-state write, secret disclosure, missing authorization, broken sandbox or source-hash drift: abort, preserve logs, involve security/operator; discard the run as qualifying evidence.
- Missing/unreadable/mismatched artifacts, unknown label provenance, holdout leakage, inadequate sample precision, incomplete strata, absent model baseline/digest, or changed flags/input digest: block qualification in affected scopes. Report reachable exploratory results with explicit limitations; do not infer unaffected scopes passed.
- Wrong-product/wrong-variant **acceptance**, forged source authority, unverified image flow or generation/hash mismatch: stop release/expansion for that scope and investigate the exact consumer path. A correct refusal is recorded as safety/coverage behavior, not falsely counted as successful extraction.
- Failed existing profile, OCR or connector gate, unexplained coverage regression, or abstention gaming: no release/change. No waiver beyond the existing audited waiver's actual authority; it cannot waive identity, image or investigation-derived holdout requirements (`profile-activation-gate.ts:116-171`).

### S5. Later operator-authorized current validation

**Prerequisites:** named operator + engineering + evaluation reviewers; fresh representative exact-SKU URLs/images and independently verified identity/variant labels; input capture dates/rights/privacy; safe workspace and backup; approved origins, credentials/secret references where needed; pinned local models already installed or a separately approved acquisition; traffic/call/compute budget, rate/deadline limits and incident owner. Nothing here authorizes model downloads, paid calls or a crawl now.

1. **Official profiles:** validate only approved domains/URLs through the existing extraction worker, first representative templates then blind family holdouts; compare fresh captures to frozen replay and run exact queue-consumer checks in a designated non-production workspace. Refresh matrix/observations and evaluate candidate/active health through the shared authority. Confirm what, if any, scheduled drift checks actually run before prescribing a scheduler. Never auto-repair/promote a failing profile. Retain URL, final URL, DOM/artifact hashes, version/policy, identity receipts and refusal reasons. Changes still require existing explicit approval.
2. **OCR models:** separate approval for loopback inference against complete reviewed assets and frozen ≥30 dataset; use the existing OCR runner/runbook with matching prompt/parser/retry flags and both baseline/candidate pinned. Record per-run variability and hardware. A cloud/provider comparison is a separate privacy/paid-call approval, not an implication of local authorization. Passing a report authorizes a review request only; any eventual one-commit flip and rollback follow the OCR runbook.
3. **Distributor connectors:** independent provider/workspace qualification, not a profile-health workaround. Follow `docs/runbooks/sourcing-engine-rollout.md:219-258`: ≥100 labeled observations per connector including ≥30 found and ≥20 negative/wrong-variant; zero false found/wrong-product/variant accepts, credential leaks or unverified-image flow; correct conflict/fallback behavior; source error ≤10% and p95 within the existing 60-second budget. Observe → manual → automatic requires explicit operator decisions, with a ≥7-day/100-item single-provider canary before expansion. These are existing sourcing gates, **not generic extraction thresholds**. Preserve immutable generations and mandatory Review.
4. **Manual route:** separately authorized per-SKU trial using the existing manual-evidence runbook; attestations are operator evidence, never an automated qualification bypass. No mass conversion of failed items.

Profile rollback must use existing reviewed version workflows, never raw profile edits that inherit old health; OCR rollback follows the model-constant revert and lazy digest-staleness behavior; sourcing kill switch/incident actions preserve history; manual evidence uses Review hold/per-item withdrawal. The next section assigns concrete acceptance and rollback per ticket.
