# Adopt cohort-centric, type-first Curation with durable product families

Onboarding acquires products item-centrically (Sourcing → Discovery → Extraction), but Curation today executes primarily per SKU: family context is discovered transiently at runtime, and siblings can be curated in separate executions against different evidence states. This ADR adopts the cohort-centric, type-first Curation architecture (issue #30): durable candidate families form deterministically after Extraction, Product Type becomes the first semantic decision, and coordinated title/Page work becomes cohort-owned while review and promotion remain item-centric.

**Status**: accepted

**Partial design supersession:** [ADR 0042](0042-evidence-first-item-local-onboarding.md) replaces cohort-owned completion/title/page authority and unrelated-member readiness barriers with item-owned authority. Frozen inputs, lease/CAS safety, review, and immutable historical records remain required; this note does not claim runtime cutover. [ADR 0041](0041-single-product-classification-contract.md) separately governs the canonical per-SKU classification.

**Context**: the current pipeline computes sibling context with in-memory caches (`cohort-name-coordinator.ts`, `cohort-page-coordinator.ts`), recomputes family membership on every run instead of persisting it, and can curate one sibling while another is still producing Extraction/OCR evidence. Product Type is known to be the root semantic discriminator, but a newly inferred type cannot drive a full first-pass Curation until a human accepts it. Issue #30 targets: "Determine what a product is before determining which properties it should have."

**Decision drivers**:

- Siblings in the same product family must never be curated against different evidence states or model calls; family coordination must be durable, not process-memory cache.
- Candidate grouping is structural (deterministic Brand + normalized name stem) and must be versioned so grouping rules can evolve without silently reinterpreting historical cohorts.
- Product Type is resolved from frozen evidence before type-specific attributes; the provisional Execution Product Type may drive Curation, while the Reviewed Product Type remains the authority for Promotion.
- Human review stays the authority for catalog publication; Review and Promotion remain item-centric.
- Cohort rows are durable history: an authority-relevant input change supersedes a cohort revision rather than mutating it.

**Decisions**:

- **Durable families.** New tables `curation_cohorts` + `curation_cohort_members` (PR1, `src/db/cohort-migration.sql`, version-gated by `curation_cohort_schema_version`) persist candidate family identity, membership hashes, per-member evidence hashes, and lifecycle status. This is the normalized replacement for the transient sibling context and the dormant `curation_runs.cohort_snapshot_json`; the dormant `curation_runs`/`curation_run_groups` tables are left untouched.
- **Candidate grouping v1.** Candidate families are formed by `normalizeBrand` + `extractNameStem` (`product-line-grouper.ts`) with grouping version `product-family-v1`. Grouping produces candidate families, not authoritative semantic identity; Product Type coherence validation (PR4) decides whether a candidate family is semantically valid. Singletons are one-member cohorts.
- **Target scopes.** Every curation target carries an explicit semantic scope: `family_invariant` (must resolve identically across members — Brand, Primary Product Type; disagreement is a conflict), `coordinated_variant` (computed once per cohort revision, members may differ — title, Category Pages), `member_local` (computed from the member's own evidence — flavor, size, weight, color, life stage, description, keywords).
- **Execution vs reviewed truth.** An Execution Product Type inferred from frozen evidence may drive Curation proposals (attribute applicability, family coherence, title/Page context) without becoming catalog truth. A Reviewed Product Type (accepted/revised by a human) remains required for Promotion. Dependent proposals must retain their dependency on the type so a type change invalidates/recomputes them deterministically.
- **Cohort-owned vs item-owned responsibilities.** Cohort-owned: family formation/finalization, Product Type resolution, family invariants, coordinated title generation, coordinated Category Page assignment, semantic consistency validation. Item-owned: Sourcing, Discovery, Extraction, Review, Promotion, and member-local attribute values, descriptions, search keywords, final draft projection.
- **Extraction completeness contract.** A member counts as Curation-ready only when the selected source state is finalized, Extraction completed, an attached Product Intelligence import completed, and a current evidence hash computed. "Selected source state finalized" means a persisted `source_url` plus Discovery completion; a `sourcingDecision` is the distributor-evidence path, not the ordinary spreadsheet-import path. Packaging OCR is informational for candidate readiness in this round — it finalizes lazily inside per-SKU curation and its gating arrives with PR3's evidence freeze (`ocrSettled` is reported but never blocks). A finalized cohort is never built from structurally present but semantically incomplete sibling snapshots.
- **Supersession semantics.** `membership_hash` is membership identity only (sorted onboarding item ids). Evidence progress (an updated `extraction_hash`) is candidate readiness state and refreshes member rows in place — it never creates a cohort revision. A changed membership (member added/removed) or an orphaned group marks the old active cohort `superseded` and inserts a new row; a unique partial index enforces one active cohort per (batch, group_key, grouping_version). Historical rows are never mutated into new truth. Skipped items are excluded from candidate membership, so skipping a member is itself a membership revision. Evidence/config drift supersedes the cohort RUN, not the candidate cohort — PR3 captures an independent `evidence_snapshot_hash`.
- **No execution behavior yet.** PR1+PR2 (this ADR's first milestone) persist candidate cohorts and derive waiting/ready state; there is no parent cohort run, no claiming, and no change to per-SKU `curateItemWithPipeline` execution. Those arrive with `classification_cohort_runs`/`classification_cohort_outputs`/`classification_proposal_dependencies` in PR3+.

**Consequences**:

- Incomplete families wait: items remain `curation / pending` while the API exposes derived "Waiting for N family members to finish Extraction" state (never `needs_input` for sibling waiting). A member that failed in a pre-Curation barrier stage (`sourcing` | `discovery` | `extraction`) produces a deterministic `blocked` state (`Member failed in <Stage> (SKU: …)`) instead of a wait; a Curation-stage failure is NOT a readiness blocker — the item is past the barrier and its evidence is complete (round-3 R1).
- Ready/blocked are mutually exclusive by construction: `ready = !blocked && sourceFinalized && extractionCompleted && piImported && extractionHashComputed && sourceProvenanceConsistent`. A failed member is never simultaneously `ready` and `blocked` (round-3 R1 invariant).
- Selected-source binding: the extraction evidence hash includes `sourceUrl`, and readiness requires the item's selected source to match the source bound to its latest `onboarding_extractions` row (normalized, trailing `/` trimmed). A mismatch blocks the member with `Selected source changed since extraction — re-extraction required` until re-extraction; cohort evaluation loads the extraction-source map in one batched query. PR3's frozen evidence snapshot (`evidence_snapshot_hash`) will include the extraction-source identity (round-3 R4).
- `curation_cohorts`/`curation_cohort_members` are created only through the version-gated migration; fresh installs and existing databases converge idempotently. Fresh installs execute `cohort-migration.sql` and write marker `'3'` directly; a marker-`'1'` database advances through the v1 → v2 → v3 hops. Deleting an onboarding batch removes its cohort and member rows.
- **Cohort schema v3 (issue #31 commit 3 / D7):** the cohort row is a candidate-family record only. `curation_cohorts.status` is narrowed to `forming | waiting | ready | superseded` — execution/lifecycle states (`running`/`completed`/`failed`/`conflicted`) never belong on it (cohort RUN state is owned by the cohort run, PR3+). `cohort-migration.sql` carries the FINAL v3 shape for fresh installs (marker `'3'`); existing databases are rebuilt hop-by-hop (`1`→`2`→`3`, or `2`→`3`), deterministically mapping any legacy execution status to `ready` when dropping the never-durable run state. The shared `CohortStatusEnum` mirrors the narrowed set.
- **Cohort schema v4 (issue #31 cleanup F3):** the candidate cohort row no longer carries ANY execution metadata. `started_at`/`completed_at` were removed from `cohort-migration.sql` (fresh installs write marker `'4'`), and existing databases are rebuilt hop-by-hop to v4 (`1`→`2`→`3`→`4`, `2`→`3`→`4`, or `3`→`4`), dropping the two columns with the same table-swap precedent (FKs off/on in `finally`, data preserved, indexes recreated, `foreign_key_check`). Execution timestamps belong solely to the future `classification_cohort_runs` — there is exactly one authority for cohort execution state. `CurationCohortSchema` and the repo row shape dropped `startedAt`/`completedAt`; `updateCohortStatus` no longer accepts them.
- **PR3 M1 — cohort run lifecycle & claim invariant (`classification_cohort_runs`, cohort schema v5):** the parent cohort run owns the execution lifecycle AND the claim lease. The status enum is `freezing | running | completed | completed_with_abstentions | completed_with_member_failures | failed | cancelled | superseded` (`queued` is dropped — claiming atomically inserts a `freezing` row with the lease). `freezing → running` happens only after the final freeze CAS transaction commits; `started_at` is NULLABLE and set on that transition (`claimed_at` records ownership start at claim). `completed_with_member_failures` EXISTS NOW (D1) — the parent completes with this status when members individually failed but the cohort-level semantic work committed. `superseded` is settable from ANY state (including terminal ones) and has no transition out. The hash-required CHECK (`status = 'freezing' OR (candidate_membership_hash IS NOT NULL AND evidence_snapshot_hash IS NOT NULL)`) forces the two mandatory evidence hashes before a run may leave `freezing` for an EXECUTION state (the CHECK exempts `superseded`/`cancelled` — terminal lifecycle states that may carry no frozen data, e.g. an abandoned unfinalized freeze); config/page/policy authority columns stay nullable mirrors. The unique partial index `idx_classification_cohort_runs_current` (`cohort_id WHERE status != 'superseded'`) enforces ONE current non-superseded run per cohort — a completed/failed run REMAINS the current historical decision until explicitly superseded (drift reconciliation or intentional retry supersedes the old row in the SAME transaction as creating the new run). Lease columns (`claimed_by`/`claimed_at`/`lease_expires_at`, TTL 15 min tunable, heartbeat piggybacked on member boundaries) give the stale sweep a deterministic predicate; reclaim resumes the same run when frozen authorities still match and supersedes on drift. `classification_runs.cohort_run_id` (PRAGMA-guarded ALTER, ON DELETE SET NULL, outside the version gate) links child per-SKU runs; the migration keeps the file additive and idempotent (`marker '4' → exec cohort SQL → '5'`; fresh installs write `'5'` directly).
- **Catalog evidence attestation projection (issue #31 commit 3 / C8):** the catalog-evidence artifact hashes a canonical projection of the live Catalog Field set (`{ xmlFields: [...] }`) instead of the raw `field-registry.json` bytes. Cosmetic registry metadata (display labels, formatting, curated field provenance) never enters the evidence hash; only Catalog Field set membership does. A missing attestation file falls back to the authoritative `field_registry` DB. `store/field-registry.json` remains a deterministic attestation projection of R1, repairable via `POST /api/field-registry/repair` (and lazily in the registry GET when the file is missing).
- **Field-registry cleanup (issue #31):** (1) the registry upsert assigns every column DIRECTLY from the merged canonical row, so a cleared value (`uiGroup: null`, null observed samples) is expressible and never resurrects the old value; (2) a durable stale-projection marker (`field_registry_projection_stale:<workspaceId>`) records when an R2 rewrite failed, `ensureAttestationFresh` verifies/repairs R2 against R1 before evidence scans and live-field reads trust it, and the registry GET/repair routes surface `projectionStale`; (3) rows created by an operator through the canonical service record the supplied patch properties as curated (`curated_fields_json`) so the next sync cannot overwrite operator-supplied metadata — only sync-discovered rows are observed-only.
- Candidate cohort refresh is additive and must never fail Extraction/Curation: worker refreshes are wrapped and swallow cohort errors.
- Ready transitions are guarded: `transitionCohortToReadyIfComplete` only moves `forming | waiting` cohorts to `ready`; `running`/`completed`/`failed`/`conflicted`/`superseded` are never moved back. Under schema v3 the execution states are no longer writable statuses; `ready`/`superseded` are the only non-forming/waiting states and neither is ever moved back.
- PR3+ builds on these tables: parent cohort runs freeze candidate evidence, configuration, Page catalog identity, and model policy; child per-SKU `classification_runs` link via `cohort_run_id`.
- **PR3 M2 — two-phase freeze engine (amendments 4–7, D4/D5/D6/D7):** `src/onboarding/cohort-curator.ts` implements the ONLY path from `freezing → running`: `freezeCohortForExecution` captures the common authorities ONCE (config authority + persisted config-snapshot ref — FAIL CLOSED when an active v2 bundle hash has no persisted `classification_config_snapshots` row, so `config_snapshot_id` is never NULL for v2; `captureVerifiedPageSnapshot` → `page_import_id`/`page_import_hash`; frozen `fieldOptions` (D7 — new optional `fieldOptions?` on `RuntimeSnapshotInput`); and the H5 combined model-execution digest `hashCanonicalJson({ policyDigest, modelExecutionPlanDigest, runtimeRuleVersionsDigest })`). Per member it then runs idempotent `ensureMemberRun`, builds + persists the member runtime snapshot WITH the frozen fieldOptions injected, pulls packaging OCR forward with a run-bound call (`classification_model_calls` attached to the member child run, mirroring the evidence-extractor invocation precedent) only when the stored OCR is unsettled OR its recorded `ocrInputHash` no longer matches the current `{sourceUrl, extractionSourceUrl, primaryImage, additionalImages}` set, persists the result back to `extraction_data_json`, and recomputes the member evidence hash. The FINAL CAS transaction reloads cohort + members + items and verifies the candidate is still ready/non-superseded, membership hash unchanged, every member's current evidence hash AND `ocrInputHash` match the frozen values, and config/page/policy digests unchanged — then persists the content-addressed `classification_cohort_snapshots` row (projection version `execution-evidence-v1`, sorted by onboardingItemId, `evidenceHash` per member), writes H1–H5 + `evidence_snapshot_id` onto the run (`freezeCohortRunAuthorities`) and transitions `freezing → running` (`transitionCohortRunToRunning`) — all in ONE transaction. Any mismatch supersedes the run (children failed): execution NEVER starts from a mixed-time snapshot. The snapshot table + `classification_cohort_runs.evidence_snapshot_id` (PRAGMA-guarded ALTER) are additive/idempotent and the marker stays `'5'`. `verifyCohortRunFrozen` is the production `verifyFrozen` for lease reclaim (crash-mid-freeze runs with NULL hashes resume vacuously; frozen runs resume only when the world still matches, else supersede). `curateItemWithPipeline` gains a prepared-cohort mode (new optional `PreparedCohortContext`): when present it SKIPS authority capture, per-SKU snapshot creation, stale-run cleanup and child `createRun`, reuses the freeze-created child run + freeze-persisted runtime snapshot, overlays the item with the frozen projection (a post-freeze mutation of `extraction_data_json`/`source_url` is never visible), and runs the 7 stages with `StageContext.cohortFrozenEvidence` set — the evidence stage (`stages/evidence-extraction.ts`) then builds evidence ONLY from the projection and materializes `classification_evidence` from the FROZEN stored packaging OCR via `packagingOcrDataToEvidence` WITHOUT a model call (trusted only when `ocrInputHash` still matches the projection's input set). Non-cohort mode stays byte-identical.

- **PR3 M3 — worker integration & acceptance (amendment 3 complete, D9):** the onboarding worker (`src/onboarding/job-queue.ts`) installs the flag-gated EXCLUSIVE cohort claim barrier. Flag OFF (default) is byte-identical legacy per-item Curation; flag ON (`cohortCurationV2Enabled` && `!cohortShadowOnly`) means `poll()` NEVER calls `claimItemsForProcessing('curation', …)` — Curation ownership is `reclaimExpiredCohortRuns → reconcile-drift-before-claimable → claimReadyCurationCohorts → freezeCohortForExecution → processCohort` while Discovery/Extraction stay per-item. `cohortShadowOnly` (PI shadow precedent) observes only: no cohort claiming at all, the legacy per-item path stays in place. Lease reclaim runs in `start()` (startup crash recovery, next to `requeueStaleInProgressItems`) and in every poll (live sibling recovery) — both flag-gated, with `verifyCohortRunFrozen` as the production `verifyFrozen` (match → resume the SAME run id / drift → supersede). D9 reconcile-before-claimable lives ONLY in the poll path (never in GET/read endpoints): every READY cohort whose current non-superseded run is in a terminal state is re-verified against the frozen world — drift supersedes (opens the claim slot, fresh run next claim); match leaves the terminal run as the current historical decision (no new run). `processCohort` (in `src/onboarding/cohort-curator.ts`) executes a `running` run: heartbeat-before/after each member (ownership-guarded lease renewal via new `heartbeatCohortRun` repo primitive), per member in ordinal order the prepared-cohort pipeline (`curateItemWithPipeline` with the frozen member projection + freeze-persisted runtime snapshot + shared authorities + sibling context), `curation_data_json` persistence exactly like the legacy worker, `updateItemStageStatus('completed')`, and member failures are RECORDED and CONTINUED (never abort the cohort unless the shared semantic state is unreachable). Parent completion (write-once `completeCohortRun`): `completed` / `completed_with_abstentions` / `completed_with_member_failures` (members individually failed but the cohort-level work committed — D1) / `failed` (cohort-level unreachable: missing frozen snapshot, members, items, or ownership; a never-frozen `freezing` run is CHECK-exempt-cancelled instead). Crash-recovery resume skips members whose child run already completed under the same parent. A completed/failed run REMAINS the current historical decision until drift supersedes it; the acceptance suite covers flag-OFF byte-identical regression, flag-ON exclusive cohort claiming with zero per-item claims, shadow mode, member-failure semantics, reclaim match/drift, completed-run-not-reclaimed, and evidence-drift → supersede → fresh-run end-to-end.

**PR3 hardening — Commit A (issue #30, recovery/atomicity):** lease reclaim is now a CAS and time math compares to NOW (`reclaimExpiredCohortRuns(workspaceId, nowIso, …)` — callers pass `new Date().toISOString()`; the query is `lease_expires_at < :nowIso`, so a lease is reclaimable the moment it passes its TTL, never only after a second full TTL). RESUME reassigns the worker only when the row still matches the observed `{claimed_by, lease_expires_at}` (`changes === 0` ⇒ skip — a run is never handed out twice); the drift branch uses ONLY the new `supersedeCohortRunIfUnchanged(runId, observed, reason)` CAS, so a stale drift verdict can never supersede a run another worker already resumed. `verifyCohortRunFrozen` vacuous-matches ONLY `status === 'freezing'` NULL-hash runs — a cancelled/failed/superseded NULL-hash run is never resumed; the reconcile path treats a `cancelled` current run as retryable and supersedes it so the claim slot reopens. Freeze-time packaging OCR persists an execution-authority digest `ocrExecutionDigest = hashCanonicalJson({planDigest, ruleVersionsDigest})` (evidence_extraction plan entry + runtime rule versions, credentials stripped) in `extraction_data_json` beside `ocrInputHash`; OCR is reusable only when terminal AND `ocrInputHash` matches AND the digest matches the CURRENT snapshot's authority (a changed model policy / local-VLM route re-runs OCR under the new authority). A reused running child whose `config_snapshot_hash` differs from the newly built snapshot is retired (`completeRun(child, 'failed', 'snapshot changed during resume')`) and recreated under the same parent when it has model-call/stage side effects; without side effects its refs are updated in place. The parent lease is heartbeated on a scoped periodic cadence (`COHORT_LEASE_TTL_MS / 3`) in `processCohort` and the freeze per-member loop; a rejected heartbeat throws `HeartbeatLostError` and the caller aborts the member/cohort deterministically (fails the in-flight child + parent) with no new side effects after ownership loss. `ExecutionEvidenceProjectionMemberSchema` gains the additive optional `ocrExecutionDigest`; the projection version stays `execution-evidence-v1`.

**PR3 hardening — Commit B (issue #30, frozen execution purity + member-projection atomic commit):** prepared-cohort mode now CONSTRUCTS the executed member FROM the frozen state — `applyFrozenProjectionToItem` is replaced by `buildFrozenItem(projection, liveItem)`: identity fields (id/upc/batchId/rowNumber/stage/status) come from the live item (pipeline state, never semantic evidence), `name`/`expectedName`/`brandHint`/`departmentHint`/`price`/`quantity` come from `spreadsheetIdentity`, `sourceUrl` comes from the projection VERBATIM (an authoritative null stays null — never `?? item.sourceUrl`), and `extractionData` is built purely from projection fields (title/brand/description/weight/bulletPoints/searchKeywords/customFields/fieldProvenance/primaryImage/additionalImages/packagingTitle/ocr{outcome,packagingOcrData,ocrInputHash,ocrExecutionDigest}/piEvidence) with NO live `...ext` spread. Sibling context is frozen too: new `buildFrozenProductLineContext(cohort, members, projections)` derives `productLineContext` + `productLineItems` from the persisted cohort + full frozen projections (skus/names/brands from `spreadsheetIdentity`, webTitles from projection titles, ocrTitles from projection OCR, descriptions from the projection); `processCohort` and prepared `curateItemWithPipeline` consume ONLY it — the live `listItemsByBatch`/`determineProductGroup` sibling reads are gone from the cohort execution path. The live `product_pages` fallback query and the distributor-copy/image-backfill live reads are `!cohortMode`-gated (frozen evidence carries what was consolidated pre-freeze; freezing attempt rows into the projection is deferred — the projection stays `execution-evidence-v1`). Title coordination feeds ONLY frozen member views. Member-projection commits are now ATOMIC: prepared `curateItemWithPipeline` leaves the child run `running` (the child id rides in `curationData.classificationRunId`) and `processCohort` writes `curation_data_json` + item `completed` + the child terminal status (derived from the pipeline result) in ONE transaction. The recovery skip rule requires all three together (child terminal-success AND `curation_data_json.classificationRunId === childRunId` AND item `stageStatus === 'completed'`); otherwise the member is re-executed — a still-running child with no projection commit is reused, and a freshly created child (after a terminal child) inherits the freeze-persisted member snapshot refs from the prior child. Test-only seam `hooks.afterMemberPipeline` (like `beforeFinalCas`) deterministically simulates a crash exactly between pipeline completion and the commit (`MemberCommitCrashSimulationError` aborts with NO member-failure write).

**PR4 — Execution Product Type from frozen evidence (issue #30, cohort schema v6):** the Execution Type is resolved ONCE at cohort freeze from frozen evidence only (`src/classification/cohort-product-type-resolver.ts`, pure module: `evidenceFromProjection` + `matchMemberDeterministically` + `resolveCohortProductType`). **Write-once at freeze:** `execution_product_type_id` / `product_type_confidence` / `product_type_outcome` (`coherent | coherent_with_abstentions | conflicted | abstained`) and the `final_membership_hash` are written by ownership-guarded write-once CAS primitives inside the final freeze transaction (DECISION-B) — a second write is a no-op, and `final_membership_hash = candidate_membership_hash` for coherent*/abstained outcomes. **Conflict = failed run + operator action later:** ≥2 confident DISTINCT ids never majority-force — the id stays NULL, the run completes `failed` with the deterministic `cohort_product_type_conflict` reason (per-member ids + SKUs), the run remains the current historical decision, and the cohort stays `ready` for an operator resolution (split family / member exclusion / revised grouping — no UI in PR4). **Dependency metadata rows:** when a member runs under a coherent Execution Type, every `field_assignment` proposal the member pipeline creates is stamped with ONE `classification_proposal_dependencies` row (`dependency_kind='execution_product_type'`, `dependency_target_id`, `dependency_value_hash = hashCanonicalJson({executionProductTypeId, productTypeConfidence})`) in the same member-projection atomic commit — metadata only, no recompute/invalidation machinery (PR6+); the PR5 paragraph below refines this to proposal-accurate separate kinds. **Shadow deterministic-only:** under `cohortShadowOnly` the resolver runs read-only over ready cohorts (`observeCohortShadowTypeResolution`, worker poll leg) — deterministic matcher only (DECISION-E: no LLM ranker, no model calls), logs a `cohort_product_type_shadow` line, writes NOTHING (run rows, PR4 columns, dependency rows, and the per-item path stay byte-identical to PR3). The confidence floor is env-tunable (`BAYSTATE_CMS_COHORT_PRODUCT_TYPE_CONFIDENCE_FLOOR`, default 0.7). API exposure is additive read-only: the cohort view carries the current run's `executionProductTypeId` / `productTypeOutcome` / `finalMembershipHash`; the Reviewed Product Type remains the sole promotion authority (no leak, §5).

**PR5 — effective Curation Product Type from the frozen Execution Type (issue #30):** the two Curation applicability stages (`attribute_applicability` / `product_attribute_proposals`) read one new pure resolver, `getEffectiveCurationProductType` (`src/classification/effective-curation-type.ts`): the reviewed (accepted) Primary Product Type — resolved by the UNCHANGED `getReviewedPrimaryProductTypeId` from in-run accepted proposals and provenance-compatible snapshot facts — wins first, the frozen cohort Execution Product Type (`StageContext.cohortExecutionType`, write-once at freeze) is the fallback, and neither yields `none`. The effective type selects the Attribute Profile from the frozen runtime snapshot only (a fail-closed guard throws before the live config cache is ever consulted with an execution type). The executor resolves the SAME value once per member (`getEffectiveCurationTypeForSnapshot` in `buildPreparedCohortContextForMember`) and exposes it read-only on `curation_data_json.effectiveProductType` (cohort mode only, DECISION-J). **Scope guards (PR5 consequences):** (1) the effective type drives ONLY the two applicability stages — `category_page_proposals`, the review completion gate, and draft Promotion never see it, so reviewed/`Promotion` authority is untouched; (2) proposal-accurate type dependency stamping with **separate kinds** (PR5 hardening, issue #30 P2): only `field_assignment` proposals — the ones the effective type actually drives — are stamped with ONE `classification_proposal_dependencies` row each inside the member-projection atomic commit; the kind is `execution_product_type` (target = the execution type id, value hash = `hashCanonicalJson({executionProductTypeId, productTypeConfidence})` — the unchanged PR4 tuple) when the effective source is `execution` (DECISION-H, execution-source only), and `reviewed_product_type` (target = the reviewed type id, value hash = `hashCanonicalJson({reviewedProductTypeId})`) when the effective source is `reviewed`; a `none` member stamps nothing. `primary_product_type` and `category_page` proposals are NEVER type-stamped — the primary type proposal is proposed from member evidence and is not downstream of the effective type, and Category Page authority is review-only until PR7 — so a type change can never falsely stale proposals the type did not drive, and reviewed-driven `field_assignment` proposals never inherit a false execution dependency (the unique `(proposal_id, dependency_kind)` index lets both kinds coexist on one proposal); (3) applicability conditions stay **reviewed-facts-only** (`factSource: 'accepted_reviewed'`, DECISION-I) — discriminator conditions under an Execution Type evaluate `unknown` until reviewed; (4) **no migration** — cohort schema v6 already provides `execution_product_type_id` / `product_type_confidence` / `product_type_outcome` and the `classification_proposal_dependencies` table; (5) flag OFF and `cohortShadowOnly` runs never carry a cohort execution type, so stage gating, dependency rows, and `curation_data_json` stay byte-identical to PR4/legacy (the effective-type path is active-mode-only by construction).

**PR6 — write-once durable coordinated titles on the parent cohort run, replay-safe after commit (issue #30, cohort schema v7):** coordinated variant titles become a durable, content-addressed parent-run artifact. **Durable outputs:** the new `classification_cohort_outputs` table (cohort schema v7, marker `'7'`) persists ONE `curated_title` row per (cohort run, kind, SKU) — `output_value_json = {title, source}` with `source ∈ {llm_cohort, cohort_fallback}` — plus a per-row canonical `input_hash` and a nullable `model_call_id` for durable LLM provenance. Historical outputs are IMMUTABLE: there is no UPDATE path, superseding a run never touches its rows, and a fresh claim/freeze creates a NEW run whose outputs are NEW rows (old rows untouched). **Canonical title input hash:** `computeCohortTitleInputHash` hashes ONLY the frozen title authority — final membership hash, the per-member frozen title slice (spreadsheet identity, web title/brand, OCR packaging title + weight/flavor), the Execution Product Type resolution (`id`, `label`, `confidence`, `outcome`), the FORMAT_RULES digest, and the H5 title slice (policy digest + the `cohort_title_consolidation` plan entry). It NEVER hashes batch rows, the old cache fingerprint, OCR provenance hashes, or non-title projection fields, and unrelated model-route changes do not invalidate titles. **Write-once / replay-safe parent op:** `ensureCohortTitlesCoordinated` runs at `processCohort` start (the single re-entrant parent entry); it REUSES the persisted set when the persisted rows are EXACTLY the expected multi-member set AND every row's `input_hash` matches (ZERO LLM calls), otherwise (set EMPTY) it coordinates under a scoped `CohortLeaseKeeper` and persists every finalized group member's title in ONE transaction (all-or-nothing — `HeartbeatLostError` propagates with no rows, the reclaiming sibling reuses-or-coordinates).
